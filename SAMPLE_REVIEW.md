«Детекция»; стр. 9 оценивает сквозные ID, завершение, подсчёт и воспроизводимость.

В этих документах нет требования binary instance masks, polygons/RLE, mask IoU,
mask AP или попиксельной разметки. Слово «силуэт» само по себе не определяет такой
формат. **Вывод инженера:** bbox + confidence + class person достаточно для
основного контура detector -> ByteTrack -> будущая межкамерная ассоциация.
Это интерпретация имеющегося текста, не отдельное подтверждение жюри: требование
к виду выделения человека в демо остаётся сформулировано неоднозначно.

Сегментация была явно указана в предыдущей пользовательской спецификации
гибридного pipeline; оттуда появились `yolo11n-seg` и обязательный `mask_rle`
в schema v1. Это дополнительное проектное решение, а не установленное требование
внешнего хакатонного ТЗ. Сейчас обоснованно пересмотреть его.

Детектор выдаёт bbox/class/score; instance segmentation дополнительно выдаёт маску
каждого объекта. Это разные задачи и веса модели, а не переключатель отрисовки.
См. [Ultralytics Detection](https://docs.ultralytics.com/tasks/detect/),
[Instance Segmentation](https://docs.ultralytics.com/tasks/segment/) и
[варианты YOLO11](https://docs.ultralytics.com/models/yolo11/).
Чтобы убрать затраты сегментации, нужны detection weights (`yolo11n.pt` или
`yolo11s.pt`) и `task=detect`; игнорирование `result.masks` у `-seg` модели
оставит вычисление сегментационной ветки.

Текущий локальный ByteTrack использует bbox/confidence. Маски сохраняются как
references, но не участвуют в matching. Для будущей приблизительной карты можно
начать с нижней центральной точки bbox с uncertainty; это не измерение положения
стопы и не замена отсутствующей геометрической калибровке. При окклюзии и обрезке
такая точка ненадёжна. Сегментация тоже не решает это автоматически.

## Как менять решение

**Основной режим — detection.** На следующем коротком GPU benchmark сравнить
`yolo11n.pt` и `yolo11s.pt` при одинаковом imgsz 640 и одинаковых source frames.
Зафиксировать отдельные model/config hashes и версии до запуска. Текущие
segmentation outputs сохранить неизменными как baseline. Small — кандидат,
а не доказанный победитель на этих камерах; автоматического скачивания/запуска
новых весов в данном review нет.

**Scene-aware проверка идёт отдельно от детектора.** Сохранять raw detections,
а решение `accepted/rejected/uncertain`, reason и версию scene config — отдельным
слоем. Для подтверждённых экранов и подвесной лампы проверять узкие области и
степень попадания bbox внутрь них. Не вводить исключения по времени/номеру кадра.
Не удалять весь кадр, дверь, лестницу или большой сектор обзора. Пересечение
бокса с лампой не равно ложному человеку: реальный человек может проходить за ней.
Image-space зоны не считать калиброванными метрическими polygons.

**Дополнительные признаки — поддержка решения, не жёсткое доказательство.**
Геометрия bbox и допустимая область ног полезны, но лампа может проецироваться
поверх видимого пола. Порог минимального размера вырежет дальних людей; требование
видимых стоп вырежет людей за столом. Отсутствие движения не доказывает ошибку:
люди могут стоять, а ТВ может двигаться. Проверка устойчивости по соседним кадрам
не удалит устойчивую ложную детекцию мебели.

**NMS лечит дубли, не семантику.** Сравнить IoU 0.5 с текущими 0.7 на clip со
стоящими рядом людьми и окклюзиями; не вводить безусловный второй NMS только по
содержанию bbox. Лампа и человек обычно не пересекаются — NMS лампу не удалит.
Оставить raw conf=0.10; track activation и правила scene filtering проверять
отдельно. Глобальное повышение confidence не устранит уверенные ошибки на ТВ
или мебели и одновременно увеличит пропуски дальних людей.

**Миграция контракта нужна до запуска detection weights.** Ввести schema v2 с
явным task=detect/segment: bbox/class/confidence и source identity обязательны,
mask обязателен только для segment и отсутствует либо null для detect. В import
сохранить поддержку v1 segmentation. `mask_ref` у локальных треков должен быть
nullable; bbox preview не должен требовать mask. Не создавать фиктивные RLE и не
отключать все проверки missing masks для старых segmentation результатов.
Оригинальные PTS, FPS камер и timestamp segment boundaries сохранить.

**Производительность измерять целиком.** Удалятся GPU mask head/postprocessing,
перенос full-resolution masks на CPU, RLE encode/decode и overlay масок.
Это должно снизить стоимость соответствующих этапов, но величина ускорения
полного run ещё не измерена. Сейчас 43:01 включают лишь 8:06 measured predict;
часть масок считается вне predict, поэтому нельзя ни обещать кратное ускорение,
ни ограничивать весь эффект только этими 8 минутами. Одновременно нужен один
полный decode камеры на обе конфигурации, bounded prefetch/batch и отдельный
exclusive timing. Чужие TensorRT/ONNX FPS из документации не переносить на этот
PyTorch/Kaggle run.

В фото-backup GIF занимают **76 905 289 bytes**, JPEG — **9 718 113 bytes**.
Это отдельный вопрос размера QA artifacts; выборочные JPEG/crops и компактный
private MP4 разумнее длинных тяжёлых GIF. Это не основной источник 43 минут.

**Приёмка следующего изменения:** короткие фиксированные фрагменты с пустой сценой,
лампой/экраном, реальными проходами у лестницы/двери, остановившимся человеком,
парой людей рядом, окклюзией и дальней зоной. Сравнить ложные frame-level boxes,
пропуски и дубли, не назначая person IDs; отдельно проверить поведение локального
трекера. Полноту и точность не называть AP/recall без соответствующей разметки.
FULL пока не выбирать. В этом отчёте режим pipeline не переключён.

## Измерения

На одних и тех же 3 659 кадрах каждой конфигурации:

- nano_640: 3 422 detection instances, 1 739 empty frames, 17.50 predict FPS,
  209.14 s predict time; peak allocated VRAM 706.38 MiB.
- nano_960: 4 615 detection instances, 1 626 empty frames, 13.24 predict FPS,
  276.37 s predict time; peak allocated VRAM 554.02 MiB.

960 даёт на 34.86% больше боксов и требует на 32.14% больше predict time.
Это не число уникальных людей и не precision/recall. Среди всех боксов score >=0.25
имеют 2 223 для 640 и 1 592 для 960; score >=0.5 — 1 642 и 1 130 соответственно.
Распределение scores тоже не является оценкой качества без проверки содержимого.

Полный run по приложенному логу занял **2 581.4 s = 43:01.4**. Суммарный predict
time — **485.51 s = 8:05.5**, или 18.8% wall time. Остальные **2 095.89 s** включают
decode, RGB, CPU masks/RLE, quality и I/O; приписывать их целиком декодеру нельзя.
В heartbeat 172 из 257 наблюдений приходятся на `decode_next_frame`: это выборочная
индикация bottleneck, а не эксклюзивный профайлер. Из объявленных stage intervals:
quality save ~60.4 s, chunk commit ~5.6 s, source SHA256 ~4 s. Суммы nested stages
перекрываются. Полного `progress.json` с accumulated timings в backup нет.

В runtime выбран `cuda:0`; nvidia-smi показывает две T4, но этот pipeline использовал
одну. Числа VRAM — пик allocated tensor memory процесса, а не доказательство,
что 960 в целом экономнее. Для строгого сравнения нужен повтор в изолированных
процессах с одинаковыми условиями. См. [PyTorch CUDA memory management](https://docs.pytorch.org/docs/2.11/notes/cuda.html#memory-management).

Предупреждение pip касается `dopamine-rl` / `gym`; этих компонентов в pipeline нет.
Оно не остановило этот запуск. Не менять gym ради данного warning.

## Рекомендуемый следующий patch

1. Изменить порядок обработки: камера -> один последовательный decode/PTS check
   до EOF -> обе конфигурации на выбранных кадрах. Сохранять независимые чанки,
   source frame indices/PTS и доказательство общей decode validation для обеих.
   Не делать быстрый seek вместо полной проверки и не кэшировать все RGB frames
   на диск: такая полная выборка заняла бы около 55 GB несжатого RGB.
2. Сохранять числовые telemetry и итоговые exclusive/включённые timings отдельным
   metadata-only приложением к export. Сейчас backup не содержит причины задержек
   с точностью полного профайлера. Decode counter должен учитывать реальное число
   проходов после изменения архитектуры.
3. Добавить явно проверенные scene filters для экранов и отдельных подтверждённых
   false-positive областей, сохраняя raw detections и причину фильтра отдельно.
   Не вырезать целиком область стола/двери: там может находиться реальный человек.
   Не удалять неподвижных людей общим правилом static background.
4. Проверить NMS IoU 0.5 против текущего 0.7 на одинаковых коротких сценах с
   дверями/частично видимыми людьми. Не объявлять это готовым лечением дублей:
   возможна потеря близко стоящих людей. Для камеры 5 проверить небольшой crop
   дальней зоны с точным обратным переносом bbox/mask в исходное изображение.
5. Сохранить conf=0.10 в raw outputs. Повышение порога при инференсе уничтожит
   слабые detections для последующей проверки и второго этапа ByteTrack.
   Выбор track activation/scene filters делать отдельно по коротким clips.
6. После исправления сцены и данных сравнить bbox detection nano_640 с небольшой small моделью
   на коротких диагностических фрагментах; batch/prefetch/FP16 проверять отдельным
   benchmark. Не тратить следующий GPU run на тот же полный SAMPLE без изменений.
7. Отделить identity исходных frame/PTS evidence от producer code hash, оставив
   оба provenance поля. Сейчас новый package snapshot меняет hash source manifest,
